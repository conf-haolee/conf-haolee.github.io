为什么AI更擅长声明式UI：从WinForms、WPF到Qt Quick/QML的工程观察

李浩同学
学习AI辅助开发 学习 AI辅助开发

发布于：2026年9月9日

次浏览

随着大语言模型逐渐参与软件开发，使用 AI 生成、修改和重构用户界面已经成为常见的开发方式。但在实际项目中，不同 UI 框架对 AI 的友好程度存在明显差异。

在工业视觉软件的现场测试中可以观察到：当 AI 直接修改历史复杂的 WinForms 界面时，经常出现控件错位、间距不统一、宽度失控、设计器预览与运行结果不一致等问题；而让 AI 理解原有工具功能后，使用 WPF 重新实现界面，通常能够获得更稳定的布局和更统一的视觉效果。同样，在 Qt 技术体系中，Qt Quick/QML 一般也比使用绝对坐标或大量运行时代码控制的 Qt Widgets 更适合 AI 生成和维护。

这种差异的根本原因，并不只是 WPF 和 QML“更加现代”，而是声明式 UI 能够把界面结构、布局关系、数据绑定和状态变化显式表达出来。它将大量独立坐标和过程性操作，转换为 AI 更容易理解的层级结构和约束规则。

本文结合 WinForms、WPF、Qt Widgets 和 Qt Quick/QML，分析声明式 UI 为什么更适合 AI 辅助开发，并讨论这一结论在工业视觉软件中的应用边界。

关键词：声明式 UI、生成式人工智能、WPF、WinForms、Qt Quick、QML、工业视觉软件

一、问题背景

传统桌面软件通常依赖可视化设计器完成界面开发。

以 WinForms 为例，开发者可以在 Visual Studio 设计器中拖放按钮、文本框、标签和面板，然后通过属性窗口设置控件的位置、宽度、高度、颜色和字体。设计器最终会把这些操作转换为 Designer.cs 文件中的初始化代码。

这种开发方式在界面规模较小时非常直观，但随着项目不断迭代，界面通常还会受到以下代码的影响：

  • 窗口加载时重新设置控件位置；
  • 根据配置动态显示或隐藏参数；
  • 根据窗口大小重新计算控件宽度；
  • 根据不同工具类型动态添加控件；
  • 根据运行状态修改按钮和结果区域；
  • 根据屏幕分辨率调整界面缩放；
  • 在多个事件中修改同一个控件。

最终，一个控件的真实状态可能由设计器、构造函数、窗口加载事件、尺寸变化事件和业务逻辑共同决定。

这时，设计器中的界面已经不再是程序运行界面的真实来源。开发者看到的预览与用户实际看到的界面可能存在明显差异，AI 同样难以仅通过代码准确还原最终效果。

现场测试中出现的典型问题包括：

  • 控件之间的间距不一致；
  • 标签与输入框无法对齐；
  • 字段名称显示不完整；
  • 修改一个控件后导致其他控件错位；
  • 设计器预览正常，但程序运行后发生重叠；
  • 不同分辨率和 DPI 缩放下布局失效；
  • AI 反复修改代码，却无法稳定接近参考图。

当同一个工具使用 WPF 重新实现后，AI 对整体布局、控件宽度、分组关系和样式统一性的控制往往明显改善。

这说明 AI 对不同 UI 表达方式的理解能力并不相同。

二、什么是声明式 UI

声明式 UI 的核心思想是：

开发者描述界面应该呈现什么结果，以及界面与数据之间是什么关系；具体的创建、排列和更新过程由框架完成。

与声明式 UI 对应的是命令式 UI。

1. 命令式 UI

命令式 UI 需要开发者告诉程序具体应该怎样操作控件。

例如：

if (isRunning)
{
    runButton.Text = "停止";
    runButton.BackColor = Color.Red;
}
else
{
    runButton.Text = "运行";
    runButton.BackColor = Color.Blue;
}

这段代码描述的是一系列操作：

  1. 判断运行状态；
  2. 找到按钮；
  3. 修改按钮文字；
  4. 修改按钮颜色。

每次运行状态变化，程序都必须再次执行对应代码。

2. 声明式 UI

在声明式 UI 中，可以直接描述按钮状态与业务数据之间的关系。

WPF 示例：

<Button Content="{Binding RunButtonText}"
        Background="{Binding RunButtonColor}"
        Command="{Binding RunCommand}"/>

QML 示例：

Button {
    text: backend.isRunning ? "停止" : "运行"
    enabled: backend.imageLoaded
}

这类代码没有强调修改按钮的执行步骤，而是直接表达：

  • 按钮文字由运行状态决定；
  • 按钮是否可用由图像加载状态决定；
  • 点击按钮时执行指定命令。

当数据发生变化时，框架会自动更新界面。

三、AI 为什么更容易理解声明式 UI

1. 声明式 UI 直接表达控件关系

典型的 WinForms 坐标布局如下：

label1.Location = new Point(20, 32);
label1.Size = new Size(80, 24);

textBox1.Location = new Point(110, 30);
textBox1.Size = new Size(160, 28);

AI 只能看到四组数字：

  • 标签位于某个坐标；
  • 标签具有固定尺寸；
  • 输入框位于另一个坐标；
  • 输入框具有另一个固定尺寸。

但这些代码并没有明确表达：

  • 标签和输入框属于同一行；
  • 标签需要统一右对齐；
  • 输入框需要占用剩余空间；
  • 两个控件之间应保持固定间距；
  • 所有参数行应遵循相同规则。

这些关系需要 AI 从坐标中推测。

WPF 可以直接表达这种布局关系：

<Grid>
    <Grid.ColumnDefinitions>
        <ColumnDefinition Width="90"/>
        <ColumnDefinition Width="*"/>
    </Grid.ColumnDefinitions>

    <TextBlock Grid.Column="0"
               Text="阈值："
               VerticalAlignment="Center"/>

    <TextBox Grid.Column="1"
             Text="{Binding Threshold}"/>
</Grid>

AI 可以明确识别：

  • 当前区域采用两列布局；
  • 左侧标签宽度固定为 90；
  • 右侧输入框占用剩余空间；
  • 标签和输入框位于同一行；
  • 参数值绑定到 Threshold 属性。

QML 同样可以表达这种关系：

RowLayout {
    spacing: 10

    Label {
        text: "阈值"
        Layout.preferredWidth: 90
    }

    TextField {
        Layout.fillWidth: true
    }
}

因此，声明式 UI 代码与人对界面的理解方式更加接近，也更适合大语言模型进行结构化推理。

2. 声明式 UI 减少了需要维护的变量

假设一个界面中有 20 个控件。

使用绝对坐标布局时，每个控件至少包含：

  • X 坐标；
  • Y 坐标；
  • 宽度；
  • 高度。

仅这些基础属性就包含约 80 个独立变量。如果再考虑边距、字体、锚点、父容器、缩放和显示状态，需要处理的变量会更多。

AI 修改其中一个控件后，可能还需要同步计算：

  • 相邻控件的位置；
  • 同一行其他控件的宽度；
  • 下方控件的纵向坐标；
  • 父容器的高度；
  • 窗口缩放后的实际效果。

声明式 UI 通过布局容器将这些独立变量压缩为少量规则。

例如：

<Grid>
    <Grid.ColumnDefinitions>
        <ColumnDefinition Width="100"/>
        <ColumnDefinition Width="*"/>
        <ColumnDefinition Width="90"/>
    </Grid.ColumnDefinitions>
</Grid>

整个区域只需要维护三列规则：

  • 标签列宽度为 100；
  • 输入区域占用剩余空间；
  • 操作按钮宽度为 90。

当窗口宽度变化时，框架会自动重新分配空间。AI 不需要逐个计算控件坐标。

从这个角度看，声明式 UI 相当于降低了界面问题的自由度，使复杂的坐标调整问题变成约束求解问题。而大语言模型通常更擅长处理明确的规则、层级和约束。

3. 声明式 UI 具有清晰的视觉树

WPF 和 QML 代码通常能够直接反映界面结构。

例如：

工具页面
├── 顶部工具栏
├── 主内容区域
│   ├── 图像显示区域
│   └── 参数设置区域
│       ├── 模板参数
│       ├── 预处理参数
│       └── 结果列表
└── 底部操作栏

对应的 QML 代码可能是：

ApplicationWindow {
    ColumnLayout {
        ToolBar {}

        RowLayout {
            ImageView {}
            ParameterPanel {}
        }

        StatusBar {}
    }
}

AI 通过代码缩进、组件名称和父子关系，就能理解页面区域之间的关系。

相比之下，传统 WinForms 的 Designer.cs 中通常包含大量连续的属性赋值。虽然其中也存在父子控件关系，但这些关系容易被大量坐标、尺寸、字体和事件绑定代码淹没。

AI 修改复杂 WinForms 页面时，容易出现：

  • 控件被放入错误的父容器；
  • 修改了错误的 Panel；
  • 新控件没有加入正确的布局区域；
  • 原有 Anchor、Dock 和坐标产生冲突；
  • 调整父容器后没有同步修改子控件。

声明式 UI 的结构树显著降低了这种理解难度。

4. 声明式 UI 具有更强的单一事实来源

WinForms 界面可能同时受以下位置控制：

Designer.cs
    ↓
窗口构造函数
    ↓
Form_Load事件
    ↓
配置加载
    ↓
Resize事件
    ↓
业务状态更新

如果这些位置都修改控件属性，就很难确定哪一部分代码代表最终界面。

设计器中看到的是初始化状态，实际运行时看到的则是多段代码共同作用后的结果。

而设计良好的 WPF 或 QML 项目通常遵循以下分工：

XAML/QML：负责界面结构、布局和样式
ViewModel/Backend：负责数据、状态和命令
Service/C++：负责算法、相机、通信和配置

静态布局主要由 XAML 或 QML 控制，业务代码不再直接修改控件位置。

这使界面具有更加明确的单一事实来源。AI 读取对应的 XAML 或 QML 文件后，看到的内容通常更接近程序最终呈现的界面。

5. 样式集中管理降低了修改成本

WPF 可以在 ResourceDictionary 中统一定义控件样式：

<Style TargetType="TextBox">
    <Setter Property="Height" Value="30"/>
    <Setter Property="Margin" Value="0,4"/>
    <Setter Property="FontSize" Value="13"/>
</Style>

QML 也可以建立统一的主题和基础组件：

TextField {
    height: Theme.controlHeight
    font.pixelSize: Theme.fontSize
}

修改一处公共样式，就可以统一调整所有输入框。

这种方式非常适合 AI 操作，因为 AI 只需要识别和修改少量公共规则，不需要逐个检查几十个控件。

在缺少统一样式体系的项目中，界面往往会出现：

  • 相同功能按钮高度不同；
  • 输入框边框和背景不一致；
  • 标签字号不一致；
  • 不同页面使用不同间距；
  • 禁用状态和悬停状态缺少统一规范。

声明式 UI 并不会自动保证界面美观，但它为统一样式提供了更清晰的实现方式。

四、WinForms、WPF、Qt Widgets 与 QML 的对比

UI 框架 主要表达方式 AI 理解难度 布局稳定性 典型问题
WinForms 绝对坐标 Designer 属性与运行时代码 较高 较低 坐标冲突、预览不一致
WinForms 布局容器 TableLayoutPanel、Dock、Anchor 中等 中等 历史代码仍可能干扰
WPF XAML、Grid、Binding 较低 较高 不规范使用固定尺寸仍会混乱
Qt Widgets 绝对坐标 geometry、move、resize 较高 较低 控件位置需要手动维护
Qt Widgets Layout QGridLayout、QFormLayout 等 中等 较高 UI 文件与 C++ 逻辑可能分散
Qt Quick/QML QML、Layout、Binding 较低 较高 QML 与 C++ 边界需要合理设计

从 AI 生成和维护 UI 的角度，可以得到一个大致顺序：

WPF / Qt Quick QML
        ↓
规范使用 Layout 的 Qt Widgets
        ↓
使用绝对坐标的 Qt Widgets
        ↓
历史复杂且运行时大量调整的 WinForms

这里需要强调，这个排序表示的是“AI 修改界面的友好程度”，并不等同于软件框架的绝对性能排名。

五、为什么 AI 重写 WPF 界面有时比修改 WinForms 更高效

在实际项目中，一个看似简单的 WinForms 界面调整，可能需要 AI 同时理解：

  • 设计器生成代码；
  • 运行时布局代码；
  • 控件事件；
  • Anchor 和 Dock 关系；
  • 自定义控件；
  • DPI 缩放；
  • 参数加载后的状态变化；
  • 业务代码中的显示与隐藏逻辑。

如果原有布局已经经过大量历史修改，AI 每次调整都可能破坏另一部分隐含逻辑。

相比之下，让 AI 先理解旧工具的功能，再使用 WPF 重新实现表现层，相当于重新建立一套清晰的布局规则。

AI 可以按照以下顺序完成工作：

  1. 识别旧工具的控件和功能；
  2. 整理参数及操作流程；
  3. 重新划分功能区域；
  4. 使用 Grid 等布局容器创建页面；
  5. 建立统一的控件样式；
  6. 使用 ViewModel 连接数据和命令；
  7. 复用原有算法和配置逻辑；
  8. 运行程序并根据截图继续调整。

重写效果更好的原因并不是 AI 更擅长“从头造一个新软件”，而是它不再需要兼容混乱的历史布局副作用。

因此，更准确的工程策略是：

重写 UI 表现层，而不是重新实现全部业务逻辑。

六、声明式 UI 并不代表绝对不会被改乱

WPF 和 QML 只是提供了更适合的表达方式，并不能自动阻止错误架构。

如果在 WPF 中大量使用：

  • Canvas.Left 和 Canvas.Top；
  • 固定 Width 和 Height；
  • 负数 Margin；
  • 后台代码修改控件位置；
  • 每个控件单独设置样式；
  • 多处重复定义资源；

那么 WPF 同样会退化成类似 WinForms 的坐标式界面。

QML 中如果大量使用：

x: 327
y: 146
width: 113
height: 31

或者同时使用相互冲突的 anchors 和 Layout，也会降低布局稳定性。

所以真正对 AI 友好的并不是某个框架名称，而是一组架构特征：

  • 使用声明式结构；
  • 使用自动布局容器；
  • 避免绝对坐标；
  • 使用数据绑定；
  • 样式集中管理；
  • 页面进行组件化拆分；
  • 业务代码不直接调整布局；
  • 静态布局只有一个主要来源。

七、Qt Quick/QML 是否比 Qt Widgets 更适合 AI

从 AI 生成和修改界面的角度看，Qt Quick/QML 通常比传统 Qt Widgets 更有优势。

QML 具有以下特点：

  • UI 结构直接体现在代码层级中；
  • 属性绑定关系明确；
  • 支持组件化复用；
  • Layout 可以自动调整子项；
  • 主题、状态和动画更容易统一；
  • QML 代码与最终视觉结构对应关系较强。

但在工业视觉软件中，Qt Widgets 仍然有其优势：

  • 传统桌面控件更加成熟；
  • 参数表格和树形控件更直接；
  • 第三方 QWidget 控件接入方便；
  • HALCON 和相机 SDK 的原生窗口可能更容易嵌入；
  • 对复杂参数工具和调试软件更加自然。

因此，在 Qt 技术体系中，可以采用以下判断：

更适合 QML 的页面

  • 设备运行主界面；
  • OK/NG 状态统计；
  • 产线状态展示；
  • 触摸屏操作界面；
  • 告警和监控页面；
  • 需要现代视觉效果的新平台。

更适合 Qt Widgets 的页面

  • 参数密集型算法工具；
  • 大量表格、树形控件和属性编辑器；
  • 依赖现有 QWidget 第三方控件；
  • 强调传统桌面操作效率的调试工具。

如果继续使用 Qt Widgets，也应该严格使用 QGridLayout、QFormLayout、QVBoxLayout、QSplitter 等布局管理器，避免通过 setGeometry()、move() 和 resize() 维护界面。

八、工业视觉软件的推荐架构

对于工业视觉软件，可以将系统划分为四个层次：

UI表现层
    ↓
状态与交互层
    ↓
业务服务层
    ↓
算法与设备层

具体职责如下：

1. UI 表现层

负责：

  • 页面结构；
  • 控件排列；
  • 字体和颜色；
  • 状态显示；
  • 用户操作入口。

可以使用 WPF XAML 或 Qt Quick/QML 实现。

2. 状态与交互层

负责：

  • 参数值；
  • 当前运行状态；
  • 按钮命令；
  • 输入合法性；
  • 页面状态切换。

WPF 中可以使用 ViewModel，Qt 中可以使用 QObject Backend 或 Model。

3. 业务服务层

负责：

  • 工具运行流程；
  • 参数保存和加载；
  • 日志记录；
  • 异常处理；
  • 输入输出管理。

4. 算法与设备层

负责：

  • HALCON 算法；
  • 相机采集；
  • PLC 通信；
  • MES 数据；
  • IO 控制；
  • 图像和模型资源管理。

这种架构允许 AI 重写和调整 UI，同时减少对算法与现场业务的影响。

九、适合 AI 的 UI 修改流程

为了进一步提高 AI 修改界面的稳定性，可以建立固定流程。

第一步：理解旧工具

让 AI 整理：

  • 控件清单；
  • 参数清单；
  • 默认值；
  • 参数范围；
  • 控件联动关系；
  • 按钮功能；
  • 输入输出；
  • 配置文件；
  • 异常提示。

第二步：建立功能对照表

功能 旧版本 新版本 验证方法
参数加载 支持 待验证 加载相同配置
参数保存 支持 待验证 比较保存文件
ROI 绘制 支持 待验证 实际操作
算法运行 支持 待验证 对比运行结果
异常提示 支持 待验证 构造错误输入
工程兼容 支持 待验证 加载历史工程

第三步：只重写表现层

保留原有：

  • HALCON 算法；
  • 参数结构；
  • 配置读写；
  • 输入输出接口；
  • 通信逻辑；
  • 核心业务流程。

重新实现：

  • 页面布局；
  • 控件样式；
  • 功能分组；
  • 数据绑定；
  • 状态显示。

第四步：建立视觉闭环

要求 AI 执行：

修改代码
    ↓
编译运行
    ↓
截取实际界面
    ↓
与参考图对比
    ↓
继续调整

AI 不能只根据代码判断 UI 是否完成，必须看到实际渲染结果。

十、结论

AI 在修改不同 UI 框架时表现出的差异，本质上来自界面信息的表达方式。

传统坐标式 UI 将界面拆分为大量独立的位置、大小和状态操作。AI 需要从这些分散代码中推测控件之间的视觉关系，并追踪运行时修改产生的副作用。

声明式 UI 则直接表达：

  • 页面包含哪些区域；
  • 控件之间是什么层级；
  • 控件应该如何排列；
  • 空间应该怎样分配；
  • 数据变化后界面如何更新；
  • 哪些样式需要统一复用。

这种表达方式减少了 AI 需要维护的独立变量，也使代码结构与最终视觉结构更加接近。

因此，与其简单地说“AI 更会写 WPF 或者 QML”，不如说：

AI 更擅长理解和生成具有明确层级、布局约束、数据绑定和单一事实来源的 UI 代码。

对于工业视觉软件，更合理的 AI 辅助开发策略是：

使用 WPF XAML 或 Qt Quick/QML 建立声明式表现层，将 HALCON 算法、相机、通信、配置和业务流程保留在独立的后端模块中。

已有历史复杂的 WinForms 或 Qt Widgets 项目，不一定需要整体推倒重写。更稳妥的方式是先识别并提取业务核心，再重新实现 UI 表现层，并通过功能对照和新旧结果测试保证迁移完整性。

未来，随着 AI 进一步参与软件开发，UI 框架是否具有清晰的结构、稳定的约束和可验证的渲染结果，可能会成为技术选型中越来越重要的评价指标。
